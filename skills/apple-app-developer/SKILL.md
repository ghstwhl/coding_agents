# Apple App Developer

A working definition, packaged as a skill, for an AI coding agent asked to build, fix, or ship an
**Apple-platform app** — Swift, SwiftUI, AppKit, UIKit, and the Xcode toolchain.

Written from a complete project cycle: a SwiftUI app shipping an **iPad app and a native macOS app
from one shared source tree**, generated by XcodeGen, talking to a Bluetooth LE radio, drawing a
MapKit map over an offline tile pyramid, released through a build-numbered CI ladder and verified on
real hardware.

*Provenance: 2026, established against Xcode 26.6 / Swift 6.3.x, deployment targets iOS 17 and
macOS 14, XcodeGen 2.46, XCTest. Toolchain facts rot fast — treat every specific below as a
hypothesis to re-verify (§15), not as a constant.*

**Prime directive: never guess.** Not an identifier, not a behaviour. An entitlement key, an
`Info.plist` key, a protocol constant, a CLI flag — look it up in the authoritative reference. A code
path or a framework behaviour — read it, or measure it, before proposing a cause or a fix.

**Why this is the prime directive and not a platitude.** Apple's platform fails *silently* on a wrong
name. A misspelled entitlement is **ignored, not rejected** — no compiler, signer, notarizer, or
reviewer objects. The app builds, signs, ships, launches, and only misbehaves at runtime on real
hardware, in a way that looks like broken hardware. One real case: a bogus
`com.apple.security.bluetooth` key sat undetected for seven weeks and surfaced as "This device does
not support Bluetooth" on a machine where a peer app paired fine. Guessing costs a build → install →
verify round trip with a human; a wrong-and-confident diagnosis costs more than saying "unverified".

**Second directive: prefer the method to the fact.** Every fact here comes with *how it was
established*, so it can be re-established on a new OS, SDK, or machine in minutes. The fact is a
hypothesis; the method is the asset.

## 0. How to use this skill

This skill is plain Markdown **on purpose**. It names no tools, no commands, and no host features, so
it works under any agent runtime, or pasted into a chat window.

**Working rules that make it portable**

- **Everything here is an operation, not a tool call.** "Build the Release configuration", "read the
  unified log", "check the signed artifact" — achieve it with whatever mechanism the host provides.
- **Degrade gracefully, and say what you lost.** No shell? Ask the human to run the command and paste
  the output. No device access? Say what remains unverified rather than implying it works. Never
  substitute a guess for a capability you lack.
- **Durable notes live wherever the host keeps them** — memory, a notes file, a decisions directory.
  What matters is that decisions and their *reasons* are written where the next session will read them.
- **If the host offers subagents, delegate investigation** (reading a large framework surface, sweeping
  a repo for `#if os(...)`) so exploration does not consume the main context.
- **Stop-and-ask actions are host-independent**: reinstalling an app, resetting permissions, pushing,
  and any claim that behaviour has been verified on hardware. See §12 and §13.
- **This skill is self-contained.** It requires no other files.

**The doctrine in twelve lines** (the rest of the file is the justification)

1. Read the code path or measure the behaviour before naming a cause.
2. A wrong identifier fails silently — verify the name, then verify the *artifact*.
3. The generator owns the project; edit the spec, never the generated output.
4. A single source tree across platforms needs one shim layer, not scattered `#if`s.
5. SwiftUI presentations that work on iOS do not present on macOS — host them in AppKit.
6. `AsyncStream` is competing-consumer: two iterators split the elements. One owner, or a broadcast.
7. Release builds differ from Debug. Build both, every time.
8. Build numbers, not clock times, identify a build to a human.
9. Never swap an app bundle under a running process.
10. Permissions and hardware approvals belong to a human; wait for them, never time them out.
11. A test that needs the app to be running is a design smell — extract the decision and test it.
12. Say plainly what is unverified. "Compiles" is not "works".

## 1. First hour on a new Apple project

Do these before changing anything. Each has saved days on a real project.

1. **Find the project's source of truth.** An `.xcodeproj` may be *generated*. Look for `project.yml`
   (XcodeGen), `Project.swift` (Tuist), or a `Package.swift`, and check whether the `.xcodeproj` is
   committed or ignored. If a generator owns it, that changes every edit you will make (§2).
2. **Establish the build/test ladder and prove it runs** before touching code. One command that runs
   everything — tests for each platform, then Release builds of each target — is the single most
   valuable thing a repo can have. A project you cannot build is a project you cannot verify.
3. **Count the targets and find the shared sources.** Multi-platform projects commonly compile *one*
   source tree into two targets. Find where they diverge, and how (§4).
4. **Read the entitlements and the signing configuration.** Which targets are sandboxed? Ad-hoc or a
   team? Which `Info.plist` keys are declared, and are those plists generated too?
5. **Find the deployment target** and what it is load-bearing for. It is often pinned by a framework,
   not by preference (§7).
6. **Identify the human-only surfaces.** Hardware the app talks to, gestures, permissions, and
   anything needing a real device. Write the checklist you will hand over at the end (§12, §13).
7. **Place the version and build-number machinery.** Where is `CFBundleShortVersionString`; how does
   `CFBundleVersion` get stamped; where does a human read the number (§11)?

## 2. The generator owns the project

If the project is generated, the spec is the source of truth and the `.xcodeproj` is an output.

- **Edit the spec, never the generated file.** Entitlements declared under the spec's
  `entitlements.properties` regenerate the `.entitlements` file on every generate; hand edits are
  discarded. If a generated file is *also* committed (common, and inconsistent), it is still an
  output — edit the spec, regenerate, and let the file follow.
- **Edits made in the IDE's UI can be silently reverted.** Changing a deployment target in Xcode's UI
  writes it into the project file; the next `generate` rebuilds that file from the spec and the change
  is gone. For target experiments use a build-time override on the command line, or change the spec.
  *Tell the human this*, or they will "fix" the setting repeatedly and watch it revert.
- **Know what the generator will and won't do.** A spec can pin product names, module names, test
  hosts, script phases and entitlements — and it cannot read your mind about any of them (§3, §4).
- **Generated artifacts deserve the same distrust as any other build output.** Check whether the
  entitlements, plists, and the project file itself are tracked or ignored *in this repo* before
  deciding what to commit.

## 3. Identifiers fail silently

An unknown entitlement or plist key is **not an error**. Nothing in the toolchain rejects it. The
system behaves as if the capability was never requested.

**How to be sure of a key**

- Look it up in the authoritative reference — Apple's entitlement and Information Property List
  documentation — rather than inferring it from naming plausibility. `device.bluetooth`, not
  `bluetooth`; the plausible-looking name is the trap.
- If verification is impossible at write time, **say so** and flag it unverified. A guess labelled as
  a guess is recoverable; a guess presented as a fix is not.

**How to be sure it took effect — check the artifact, never the source**

- Read the entitlements **embedded in the signature** of the exact bundle that ran, not the file on
  disk. A stale app in `/Applications` from a previous build is the usual explanation when the source
  is correct and the symptom persists.
- A build can be signed, launch fine, and still have been built before the fix landed. Identify *which*
  artifact is running by its build number (§11).

**Read the failure signature, because the states mean different things**

| Symptom from the framework | Actual cause |
|---|---|
| Bluetooth reports "unsupported" / never reaches powered-on | The sandbox entitlement is missing or wrong |
| A permission prompt never appears, or the app is killed on first use | The usage-description plist key is missing |
| The framework reports "denied" | The human declined a prompt; it needs System Settings or a TCC reset |
| Reports "off" | The hardware is off |
| The file panel appears but the read fails | The sandbox file-access entitlement is missing |

**Sandbox grants are per-capability and per-process.** A sandboxed app needs an explicit grant for
every resource class it touches — device access, outbound network, user-selected files (read, and
separately read-write; a save panel that returns "cancelled" immediately is the classic
missing-read-write symptom). Entitlements do **not** flow into embedded executables: a helper or
service that touches the resource needs its own copy.

**Permissions are keyed to the code signature.** With ad-hoc signing there is no team identity, so a
rebuilt app can re-prompt or be silently re-denied. Know the reset command for the platform, and
expect a re-approval after every rebuild (§12).

## 4. One source tree, two platforms

A project that ships an iOS target and a macOS target from shared sources has one real question:
**where does the divergence live?** Scatter it and every file becomes a minefield.

**Pattern: one shim layer, not scattered conditionals.** Put the API differences behind typealiases
in a single file — a colour, a font, an image, a view, a label, a bezier path, a gesture recognizer,
a modifier-flags type — mapping the UIKit and AppKit names onto one `Platform*` name each. Then write
behavioural shims for the handful of places the two genuinely diverge. Call sites stay single-sourced,
and `#if` appears where the platform *behaves* differently rather than where it merely *spells*
differently. Keep the platform-neutral party the default branch, so the minority platform is the
visible exception.

**The macOS twin is not "iOS with a bigger screen".** Divergences that are real, in rough order of how
much time they cost:

1. **Presentation.** See below — this is the big one.
2. **File import/export.** The SwiftUI modifiers for these are the primary casualty of (1).
3. **Window chrome and sizing.** Sizing that only applies on macOS, and window-level lifecycle.
4. **Keyboard and modifier routing.** Menus, shortcuts, and responder-chain behaviour.
5. **API surface.** Handled by the shim layer.

### SwiftUI presentations do not work from a macOS main window — use AppKit

Measured on a real twin, across six review rounds: **every SwiftUI presentation from the main window
failed on macOS, each in a different way.**

- The file-import and file-export modifiers **never present** from the main window — probed at the
  detail column, the toolbar, and the split-view level. They present only when hosted inside a sheet.
- An alert **re-presents** a dismissing dialog when the row that triggered it vanishes mid-dismissal.
- A sheet **loops open-and-close** on dismissal (one editor reopened five times before staying shut).
- A sheet **containing a list collapses to its toolbar**, because macOS sizes sheets to the list's
  under-reported ideal size — it needs a root-level frame with explicit minimum and ideal dimensions.

**The recipe: host the content in AppKit and take SwiftUI's presentation machinery out of the path.**

- File import → the platform's open panel. File export → the platform's save panel.
- Alerts → the platform's alert, run modally.
- Anything bigger (an editor, a download window) → a real window with the SwiftUI content as its
  hosted content view, owned by a controller the caller *retains*, with a close callback so the host
  can drop the retention. Set the window to not release on close, and give it a minimum size.

**Two more rules that make this stick:**

- **Route through one flag, one consumer.** A trigger anywhere in the app sets a request flag; a
  single app-level consumer presents. This keeps one presentation path per platform instead of one per
  call site — and it is how a trigger added later inherits the correct behaviour for free.
- **Never introduce a new SwiftUI sheet, alert, or file presentation from the main window on macOS.**
  When reviewing a change that adds one, that *is* the bug.

**Deferring by one beat is sometimes load-bearing.** Presenting a modal panel in the same transaction
as a sheet or dialog dismissal can drop it. And clear a one-shot request flag *inside* the platform
branch that consumed it — clearing it on the other platform cancels the presentation there.

**The picked file's access is temporary — copy the bytes.** A URL from an open panel is
security-scoped. On macOS the system starts that access for you; on iOS you start it yourself. Either
way the grant ends when the call returns, so anything kept beyond the import must be bytes copied into
the app's own container, or a security-scoped bookmark — holding the URL is not enough. Stop only the
access you started: the start call returns *false* when no scope was needed, and treating that as
failure breaks an unsandboxed build. A save panel that returns "cancelled" the instant it opens is the
missing read-**write** grant, which is a different key from read-only.

**A request flag scoped to the app is only safe while there is one window.** If several windows host
the same presenter observing one flag, a single trigger fires every window's handler. Keep a
single-main-window app single; if multi-window becomes real, move the flag into the window's own
scope and let the menu reach the key window's instance through a focused value.

## 5. Streams are competing-consumer

`AsyncStream` delivers each element to **exactly one** iterator. Two concurrent `for await` loops over
the same stream do not both see the data — they split it.

*Measured, not recalled:* two iterators over one 100-element stream received 47/53, 41/59 and 43/57
across three runs. Every element went to exactly one iterator; nothing was duplicated, nothing was
lost overall — it was simply divided. Treat a comment claiming a stream "fans out" as a defect in the
comment.

**Consequences and the fix**

- A second consumer added to an existing stream **silently starves the first**. The symptom is data
  that lags, updates that arrive intermittently, and timeouts that fire while data is flowing — at
  scale, and never in a small test.
- Fix it with **one owner that re-emits**: a single consumer iterates the stream and republishes to
  every interested party through whatever broadcast mechanism the codebase already uses. Do not add a
  second iterator.
- Where a stream must have one consumer, enforce it as a stated invariant at the stream's declaration,
  so the next person to reach for it sees the constraint before writing the code.

**Related:** model state changes are not streams. Driving a reaction from an observed state change is
not a second consumer and does not split anything — but it also does not fire per element, which is
the difference that matters when you are choosing between the two.

## 6. Debug and Release are different programs

A Release build is not "the same code, faster". Optimization can expose a defect that Debug hides —
and on Apple platforms the interesting failures are the ones that only exist at `-O`.

- **Build both configurations in the ladder, for every target.** Debug-only CI let a compiler crash
  block an App Store configuration entirely undetected, and separately let a runtime miscompile reach
  a shipped build. Two extra builds cost minutes; not having them costs a release.
- **A compiler workaround is not a fix.** An annotation that dodges a compile-time crash can leave the
  *runtime* behaviour broken — one real case: a Swift subclass of an Objective-C class with a
  factory-bridged initializer miscompiled at `-O` into sending the factory selector to the instance,
  crashing on first use. The working fix was to **remove the subclass** and use the plain
  Objective-C class with a side table for the extra metadata.
- **The general rule:** if you introduce a Swift subclass of an Objective-C class whose initializer is
  factory-bridged (a `MKPolyline`, a `UIBezierPath`-style convenience init), do not trust a
  suppression. **Runtime-test it in a Release build** — and prefer not subclassing.
- **Build both, warn about neither.** Treat new warnings in the Release build as findings, not noise.

## 7. Platform behaviour that is measured, not documented

Some limits are real, undocumented, and only findable by experiment. Two that cost real time:

**MapKit's maximum zoom is a *scale*, not a level.** The clamp is applied to the view's scale, so the
deepest zoom-in varies with viewport size — measured at roughly 66 m, 103 m and 155 m of visible
ground for 900 pt, 1440 pt and 1800 pt of viewport height, i.e. a roughly constant metres-per-point.
The consequences are counter-intuitive: a *larger* display mode zooms **less** deep, and comparing
setups by a zoom-level badge is meaningless when the badge is itself viewport-dependent. Compare by
ground distance. Any "how far in can we zoom" question is answered by measurement on the target
device, not by reading a level number.

**A tile overlay that replaces map content must declare a truthful depth.** An overlay that takes over
rendering has a `maximumZ`; leave it at the default and an OS that has nothing deeper to draw will
render **nothing at all** past that point — the map greys out on one OS version while another quietly
magnifies the deepest tiles. Declaring the true maximum (including any depth the overlay synthesises
by cropping) fixes it. And an overlay that replaces content should say so: never silently fall back to
network tiles.

**Deployment targets are often load-bearing.** A floor of iOS 17 / macOS 14 usually means the
*Observation* framework is used throughout — observable types, environment injection, bindable
properties. Lowering such a floor is not a setting, it is a mechanical migration across every state
type; measure the cost with an override build before promising it.

## 8. Undo, menus, and the responder chain on macOS

Menu commands and keyboard shortcuts do not travel the chain you expect on macOS.

- **A standard edit command can die on the window.** A window answers `responds(to:)` for undo
  through a no-op default, so the action is accepted and discarded — and AppKit **beeps** while the
  real undo manager sits there with work to undo. Claim the key equivalent in the container view
  instead of relying on the menu command, and route it to your own stack.
- **Only a focused text editor may divert undo.** While the human is typing in a text field, undo
  belongs to the field. Detect that case specifically (the resolved target is a text view, or a field
  editor) — a generic "walk the chain for anything implementing undo" is wrong for exactly the
  no-op-default reason above.
- **SwiftUI makes the window the first responder**, so chain-based routing misresolves there. Do not
  build logic that depends on the chain reaching a view.
- **A keyboard shortcut claimed twice dispatches unpredictably.** If a menu item owns a shortcut,
  remove it from the button.

**Testing undo:** an undo manager left with event-grouping enabled installs a run-loop observer that
closes its group long after the test ends — crashing an *unrelated* async test with "no matching
begin". Test undo managers must disable automatic grouping and group explicitly.

## 9. Diagnosis on Apple platforms

**Read the unified log, and know what shadows it.** The platform's log tool is the cheapest ground
truth for runtime questions, but a shell's builtin of the same name can shadow it — and the resulting
error may vanish when stderr is redirected, so queries silently return nothing. Use the absolute path
to the real binary. Filter by the subsystem the app logs under.

**Your test host may be the app itself.** Unit-test targets commonly run inside the **real application
binary** — same process name, same sandbox container, real-looking log lines. When watching live logs
during bring-up, filter to the instance you actually launched, or you will debug a mock.

**Prefer instrumenting the real app to reasoning about it.** Add a log line, run it, read it. A
hypothesis that costs a build → install → verify round trip with a human is expensive; a log line is
not.

**Keystroke-driven behaviour is often un-automatable.** Synthesising key events is frequently blocked
by accessibility permissions from a terminal. The efficient loop is: the human presses the keys while
you run a log tap, and the trace tells you which responder actually received the event. Hand the human
a precise key sequence, not "try the shortcut".

## 10. Testing strategy

- **Extract the decision, not just "the logic".** The most valuable testable seam is a pure predicate —
  access rules, allow/deny, "does this qualify" — taking a state value and returning a decision. Test
  it with a table of `(state → expected)` rows. *When a bug is found in such a predicate, add the row
  that would have caught it, in the same change.*
- **A test you cannot write is a design smell.** If exercising a decision needs a running app, the
  decision is probably buried in a view or a delegate; move it out first, then test it.
- **Everything compiles into both platforms' test targets.** In a shared-source project, every test
  file builds for *both*; gate platform-specific tests as whole files, or the other platform fails to
  compile.
- **Test host identity is configuration.** When a product name and a target name diverge, the test
  host must be pinned explicitly — the tooling derives it from the target name and will not find the
  app. Likewise, keep the module name stable across targets so one import works everywhere, and keep
  the iOS product name identifier-safe (display names carry the spaces instead).
- **Pin the decisions that came from a ruling**, not just the mechanics: a default value, a key's
  shape, a documented invariant. That turns "we decided this once" into "the build tells you if it
  changes".
- **One command runs the ladder** (§1.2), and it ends with Release builds of every target (§6).

## 11. Build identity and release discipline

- **Cite builds by their build number, never a clock time.** A human identifies a build by its
  incrementing `CFBundleVersion`; "fixed at 11:17" is ambiguous across rebuilds in the same minute and
  unverifiable from inside the app. To know which build you actually produced, read `CFBundleVersion`
  from the **built** plist. Do not assume the app *displays* it — whether the number is surfaced in an
  About screen is a per-project detail, and a spec comment claiming it does can be aspirational.
- **Stamping the build number has two traps, and both are silent.**
  1. It must run **before** the plist is processed, and it must write the **source** plist. A
     post-build phase runs before the build copies the source plist over the built one — which
     **erases the stamp** and ships a build with the wrong number.
  2. The stamping step must declare the plist as its **output**, which is what makes the plist
     processing wait for it. Without that edge the two tasks race and builds intermittently ship the
     *previous* build's number.
- **One version, one home.** A marketing version declared in the spec; every mirror of it validated
  against that home. Bump it in one place per release, in the same change as the code.
- **A published build is immutable.** A documentation fix cannot be retro-fitted to a released
  version; it rides the next one.
- **Any functionality change updates the documentation in the same change** — the README, the operator
  manual, the install/build instructions. Documentation that contradicts the app is a defect the users
  see.

## 12. Never run an app bundle swap under a live process

Replacing the `.app` in place while the user's instance is **running** breaks the app in ways that look
like a code bug: on a Metal-backed map, the map renders as a static grey rectangle with zoom dead
while other controls keep working.

- Quit the running instance **first** — ask the human to quit it; do not assume a kill is enough, and
  never install over a running app.
- After any install, verify with a **fresh launch** before investigating a rendering bug in the code.
- Record this on the human's checklist, because it will recur at every install.

## 13. Working with a human, and what "verified" means

- **Hardware and permissions belong to a human.** A rebuilt app needs permission re-approval; a
  physical device needs hands. The human is not always at the machine — so when behaviour is
  consistent with a pending approval, **wait and watch the logs**. Do not time out, and do not report
  an error you have not established.
- **Give a checklist, not a claim.** For every behaviour needing a human, write the check — including
  the interesting edges: empty state, no free slot, denied permission, a second device, a cold start.
- **Distinguish what you verified from what you inferred.** "Compiles", "the tests pass", "I read the
  code path" and "it works on the device" are four different claims. Never report hardware behaviour
  as verified on the human's behalf.
- **Report a negative result honestly.** A build passes or it does not; a test was skipped or it was
  not. If a step was skipped, say so.
- **Record rulings with their reasons.** When a decision is made — a default, an accepted limitation,
  a divergence — write the decision, the evidence, and the cost of being wrong. Dated notes are how a
  project survives a context loss.
- **Prefer primary artifacts over summaries**: the signed bundle, the log, the plist, the built
  product. Say which source an answer came from.

## 14. Anti-patterns

- Guessing an entitlement, `Info.plist`, or framework identifier because it looks plausible.
- Verifying a capability in the source file instead of the signed artifact.
- Editing a generated project file, or a generated entitlements/plist file, by hand.
- "Fixing" a setting in the IDE's UI on a generated project, and watching it revert.
- Attaching a SwiftUI sheet, alert, or file presentation to a macOS main window.
- Adding a second iterator to an existing stream.
- Shipping a compile-time suppression for a runtime problem.
- Testing only Debug, or building only one target in Release.
- Identifying a build to a human by a timestamp.
- Running a test host that is also the app, and then trusting the logs without checking which instance
  produced them.
- Installing a new bundle over a running instance.
- Reporting hardware behaviour as verified when only the human can run it.
- Changing functionality without updating the docs that describe it.

## 15. References, best first

1. **The code path itself**, read end to end, plus a probe or a log line from the running app. The
   only authority on what this app does.
2. **Apple's own documentation**, fetched as data rather than recalled — the entitlement reference,
   the Information Property List reference, and framework pages. The authority on what a key is called
   and what it does.
3. **The signed artifact** — the embedded entitlements and the built plist. The authority on what was
   actually shipped.
4. **The unified log** from the exact instance you launched. The authority on runtime behaviour.
5. **A known-good peer implementation** on the same stack — read it to learn *what* it does, and
   verify from its code rather than its description. Respect its licence: reading behaviour is not the
   same as copying code (§16).
6. **The project's own decision record and operator manual** — the fastest route back into intent.
7. **Community answers** — a hypothesis generator, never an authority on an API detail.

## 16. Licensing, when you borrow behaviour

- **Verify the licence before copying, and re-verify it** — licences change, and a note that was true
  last month may now be wrong in the dangerous direction. A repo relicensed from a copyleft licence to
  proprietary makes its previously-compatible peer **incompatible** overnight.
- **Reading behaviour is not copying code.** You can learn exactly what a peer does from its public
  behaviour and reimplement it. That is the safe path whenever licences are unclear or incompatible.
- **Track third-party components** in the place the project keeps them, and keep the notice file
  honest.
- **A distribution channel can forbid a licence** independently of the code: some licences are held
  incompatible with some stores. Verify the distribution path before submission, not after.

## 17. Unknowns to re-establish per project (do not carry them as facts)

- Whether the project is generated, by what, and which of its outputs are tracked.
- The deployment targets, and which framework pins them.
- Which targets are sandboxed, what each grants, and which `Info.plist` keys are declared.
- Whether the test targets run inside the real app as a test host.
- The current ladder: exactly which commands constitute "everything passes".
- Which SwiftUI presentations already fail on this project's macOS target, and how it works around
  them.
- Which stream types exist, how many consumers each has, and whether that is enforced.
- Where the build number is stamped, from what counter, and where a human reads it.
- Which behaviours are hardware-only, and what the human's checklist must therefore cover.
- The licence of this project and of every peer it draws from — checked today, not remembered.
